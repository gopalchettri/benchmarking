Below is a reframed version written in a formal SDD style.

## 1. AI / LLM Design

The system shall use the Large Language Model only for controlled natural-language generation of defensive threat scenarios. The LLM shall not determine threat applicability, ranking, control selection, evidence requirements, or validation outcomes.

The LLM shall receive only a pre-approved structured scenario input pack generated by the deterministic application services. This input pack shall contain validated asset, service, sector, threat, actor, control, ranking, and evidence information.

The LLM prompt shall include:

- System-level defensive generation instructions.
- A fixed response schema.
- Approved scenario context.
- Explicit restrictions against exploit instructions, payloads, bypass steps, procedural attack guidance, or executable code.

All LLM output shall be validated before it is stored or returned to the user.

## 2. Separation of Rules and AI Logic

The solution shall maintain a strict separation between deterministic business logic and AI-generated language.

The deterministic engine shall be responsible for:

- Input validation and normalization.
- Context building.
- Threat identification.
- Threat applicability checks.
- Threat ranking and prioritization.
- Control identification.
- Evidence and gap identification.
- Scenario ID generation.
- Final output validation.

The AI component shall be responsible only for converting the approved scenario input pack into readable defensive scenario text.

If the deterministic engine rejects a threat as not applicable, the system shall not call the LLM.

## 3. Threat Ranking and Prioritization

Threat ranking shall be performed by the deterministic ranking engine. The LLM shall not calculate or modify ranking values.

The ranking engine shall evaluate each scenario using configured scoring logic and contextual factors such as:

- Asset criticality.
- Service criticality.
- Threat type.
- Threat actor relevance.
- Applicability status.
- Existing controls.
- Identified control gaps.
- Potential operational, safety, confidentiality, integrity, and availability impact.

The ranking output shall include:

- Likelihood score.
- Impact score.
- Priority score.
- Priority rating.
- Ranking justification.

## 4. Explainability and Auditability

The system shall provide traceability for every generated scenario. Each scenario shall be explainable from the original request through final output.

The audit record shall capture:

- Request payload.
- Scenario ID.
- Tenant, entity, asset, service, and user context where applicable.
- Matched threat category and threat type.
- Applicability decision and reason.
- Ranking scores and ranking reason.
- Selected controls.
- Required evidence.
- LLM provider and model metadata, excluding secrets.
- Validation result.
- Final response payload.
- Processing status and timestamps.

This audit trail shall support security review, compliance review, troubleshooting, and historical reporting.

## 5. Performance and Scalability

The system shall support asynchronous scenario generation for production workloads. The API shall accept a request, create an audit record, enqueue the task, and return a task identifier for later status polling.

The system shall support:

- Background task processing through workers.
- Tenant-level active task limits.
- Batch scenario generation.
- LLM timeout handling.
- LLM circuit-breaker protection.
- Optional response caching.
- Horizontal scaling by increasing worker capacity.

Rejected applicability cases shall not call the LLM, reducing cost and processing time.

## 6. Security and AI Governance

The system shall enforce AI governance controls across the full scenario-generation lifecycle.

Security controls shall include:

- API keys shall never be hardcoded.
- API keys shall never be logged, returned, or stored in audit payloads.
- The LLM shall receive only approved scenario context.
- Prompt templates shall restrict the LLM to defensive, high-level scenario generation.
- Output validation shall block unsafe, unsupported, or invented content.
- Generated content shall not include exploit steps, payloads, bypass methods, attack code, or operational attack instructions.

The deterministic validator shall remain active for all providers, including mock mode, OpenAI mode, and Azure OpenAI mode.

## 7. Prompt Injection and Data Leakage Controls

All user input shall be treated as untrusted. User-provided values shall be normalized, validated, and converted into a controlled scenario input pack before being sent to the LLM.

The system shall prevent prompt injection by ensuring that user input cannot override system instructions or safety rules.

The system shall prevent data leakage by ensuring that:

- Secrets are never sent to the LLM.
- Raw environment variables are never sent to the LLM.
- Unrelated tenant data is never included in the scenario input pack.
- Internal logs and configuration values are not exposed in generated output.
- LLM responses are validated before release.
